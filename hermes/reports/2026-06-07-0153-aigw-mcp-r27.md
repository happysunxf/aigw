## 二、本轮最重信号：第三方 MCP gateway 生态密度爆发

r27 抓到的「**MCP gateway 关键词 search results**」在 48 min 内出现 6+ 条**架构意义的新增议题/合并**——AIGW 4 家自研以外，第三方实现正在快速补齐 spec 仓 6 月静默期留下的能力空白。

1. **IBM/mcp-context-forge #4987 (open 6/6 17:37 UTC) `fix: dispatch affinity-owned /rpc in-process to preserve session reuse` (+472/-213/6)** —— **stacked on #4981**。`#4981` 已修跨 worker MCP 转发的两个 bug（`WORKER_ID` 广播 + 转发的 HTTP loopback 分散）；本 PR 把**剩下 3 处 affinity dispatch 站点**也收齐——之前走 `127.0.0.1:4444/rpc` loopback，被 kernel 路由到**随机 worker**，对**有状态 upstream** 来说会 spawn 重复 upstream session。修法：`mcpgateway/utils/internal_http.py` 加 `post_rpc_in_process()` 用 `httpx.ASGITransport(app)` 在当前进程跑 FastAPI（无 socket / 无 kernel 重路由）；4 个站点（`_execute_forwarded_http_request` / `_execute_forwarded_request` / owner-local path / `[HTTP_AFFINITY_FORWARDED]` block）都走这个 in-process helper。**AIGW 落点**：**MCP gateway session affinity 必须 in-process dispatch**——任何 loopback HTTP 都破坏「session owner 真正执行」的 invariant。Envoy AI GW / Kong / Higress 三家均无此修复。
2. **jeong-sik/masc-mcp #20384 (open 6/6 17:37 UTC) `feat(otel): add MCP semconv transport attrs and metric` (+929/-71/30)** —— 4 个 MCP 官方 duration histogram 全部落地：`mcp.client.operation.duration` / `mcp.server.operation.duration` / `mcp.client.session.duration` / `mcp.server.session.duration`；client session 持久化 `mcp_client_session_started_at` 在 local worker metadata；**client session metric 故意 omit `mcp.session.id`**（避免高基数），operation telemetry 仍包含；explicit DET/NDT 边界。**依据** OpenTelemetry MCP semantic conventions official 1.41.1（checked 2026-06-07 KST）。**AIGW 落点**：**OTel MCP semconv 1.41.1 是事实标准**——AIGW 4 家网关要把这 4 个 histogram + 4 类 transport attrs 都吐到 OTel collector。
3. **agigante80/actual-mcp-server #173 (open 6/6 17:02 UTC) `Feature: persistent session store (Redis / SQLite) for HTTP transport`** —— 现实现所有 active session 在 process-local `Map`，**容器 recreate（compose up after env change / image update / host reboot）就 drop 全部 session**，Claude UI 需手动「Disconnect → Reconnect」跑 OAuth。提了具体 reproduction（`AUTH_PROVIDER=oidc` + `docker compose up -d --force-recreate` → `warn: [SESSION] Session <id> not found`）。**AIGW 落点**：**HTTP transport session store 必须可插拔 + 持久化**——Redis 最小集，理想可插拔；**「容器重建 = session 丢」是 2026 H1 MCP gateway 默认缺陷**。
4. **FlowMCP/x402-mcp-middleware #11 (open 6/6 17:47 UTC) `Potential settlement-ordering issue: MCP tool handlers can run before settlement`** —— `src/v1/task/X402Gateway.mjs` 的 middleware **verify → next() → handler 跑**；settlement 挂在 `res.on('finish', ...)`，**settlement 失败只 console.error**。v2 用 `res.json` interceptor 仍先调 handler。**AIGW 落点**：**MCP gateway x402 类付费工具的 verify-before-settle 顺序是已知安全漏洞**——settlement 失败时 handler 已跑完 side effect，需 EITHER (a) 走 `res.locals.x402` interceptor 验证失败直接 402 不调 next()，OR (b) 把 settlement 提前到 handler 前。**r27 是首次有 issue 正式提出此 ordering bug**。
5. **gethouston/houston #462 (open 6/6 17:30 UTC) `feat(centinela): capability firewall with MCP gateway and WhatsApp step-up` (+2693/0/27)** —— **CaMeL (Google DeepMind) + Agents Rule of Two (Meta)** 双范式的「**capability firewall for Houston agents**」；两个新 engine crate：`houston-centinela`（纯逻辑 Policy Core，`evaluate() → Allow | Deny | StepUp`，DENY 总是先 STEP_UP 检查，**fail-closed by construction**，25 tests）+ `houston-centinela-mcp`（MCP gateway JSON-RPC over stdio 包装 core，**每个 tool call gated before it runs**；STEP_UP 通过 Meta Cloud API 走 WhatsApp 等 SI/NO；deny + timeout fail-closed；17 tests）。**AIGW 落点**：**「MCP gateway as code-enforced trust boundary」是 2026 H2 范式**——MCP gateway 不只是协议代理，**而是 LLM 控制的 confused-deputy 反制**。
6. **forkforkdog/echidna #3 (open 6/6 17:28 UTC) `Add streamable MCP bounds`** + **mirusser/Kubernetes-MCP-Guard #74 (open 6/6 17:17 UTC) `Feat/agent guardrails` (+11160/-1299/144, .NET 8)** —— 前者给 streamable HTTP 加 bounds（资源/速率）；后者 `.NET 8` 实现 Kubernetes-native MCP gateway + agent guardrails，**plan-first + approval-gated mutation**、**auth + scope 在 HTTP gateway 强制**、**RBAC + namespace**。

**生态节奏**：6 条横跨 5 仓库（IBM / jeong-sik / agigante80 / FlowMCP / houston / echidna / Kubernetes-MCP-Guard）的 PR 集中 6/6 17:00–17:55 UTC 打开——**AIGW 4 家之外**的 MCP gateway 实现正在**自我补齐**：session affinity（IBM）、OTel semconv（jeong-sik）、persistent session（agigante80）、settlement ordering（FlowMCP）、capability firewall（Houston）、Kubernetes-native（mirusser）。**r27 是首次出现「MCP gateway 已经是基础设施层」语义的轮次**。

## 四、MCP 治理 5 大硬要求（AIGW 落点）— r27 增量

累加自 r26（AG-1~AG-46 + 本轮 5 条新 = **AG-47~AG-51**）：

- **AG-47 In-process session affinity dispatch**（IBM mcp-context-forge #4987 范式）—— MCP gateway 多 worker 部署时，**任何「session owner 重派发」必须 in-process**（httpx ASGITransport / 本地 FastAPI invoke）—— **loopback HTTP 不可接受**，因为 kernel 会路由到随机 worker，对有状态 upstream spawn 重复 session，破坏「session owner 真正执行」的 invariant。
- **AG-48 OTel MCP semconv 1.41.1 4 histograms + 4 transport attrs**（jeong-sik/masc-mcp #20384 范式）—— AIGW 必须 emit `mcp.client.operation.duration` / `mcp.server.operation.duration` / `mcp.client.session.duration` / `mcp.server.session.duration`；client session metric **故意 omit `mcp.session.id`** 避免高基数，operation telemetry 仍包含。
- **AG-49 Persistent session store for HTTP transport**（agigante80/actual-mcp-server #173 范式）—— session store **不能只放 process-local Map**——容器 recreate / image update / host reboot 不应让所有 client 走 Disconnect→Reconnect；**Redis 最小集**，理想可插拔 backend。
- **AG-50 Verify-before-settle ordering for x402 / paid tool calls**（FlowMCP/x402-mcp-middleware #11 范式）—— 付费 / 高价 tool call **settlement 失败不能让 handler side effect 已落库**；**settlement 必须发生在 next() 之前**或 res.json interceptor 验证失败直接 402。
- **AG-51 Capability firewall at MCP gateway layer**（gethouston/houston #462 范式）—— MCP gateway 应是 **code-enforced trust boundary**，**不是 prompt-time filter**；`evaluate() → Allow | Deny | StepUp`，**DENY 必须先于 STEP_UP 检查**，fail-closed by construction；高危操作走 WhatsApp / Slack step-up 等 owner approval 通道。
